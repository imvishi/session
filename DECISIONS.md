# Decisions

## Professional availability

**One block of hours per day.** A professional has at most one start and end time for each day of the week. This matches the brief's example (Monday 09:00-17:00) and keeps the screen simple. A lunch break would need several blocks per day, which the unique index on professional and day would have to allow. Hours can't run past midnight.

**Hours are stored as wall-clock minutes, not UTC.** "Monday 09:00" stays 09:00 for the professional all year, so it can't be stored as one fixed UTC time. It only becomes a real moment once it's combined with a date and the professional's timezone. The API uses the same minutes, so nothing has to parse or convert times, and `time_options` gives the frontend a value and a label for each choice. The trade-off is that a raw request shows `540` rather than `09:00`.

**Slot layout.** Slots start every 60 minutes from the start of the working day: a 50-minute session, then a 10-minute break so the professional isn't going straight from one session to the next. A slot must finish within the working hours, so 09:00-17:00 gives 8 slots, and the last runs 16:00-16:50. Starting at 09:30 gives 09:30, 10:30 and so on, because the grid follows the professional's hours rather than the top of the hour.

**Slots are calculated when needed, not stored.** Changing working hours then takes effect immediately, with no stored rows to keep in sync and no background job extending the calendar.

**The backend owns every availability rule.** `SlotGenerator` decides the slot layout, and `WeeklyAvailability` gives the frontend a complete week to display: the days and their order, default hours, the times a professional can pick, the break length, the timezone label and each saved day's `slot_count`. Times must be in 30-minute steps, which the API enforces as well as offers. The frontend only shows the form, tracks unsaved edits and sends them. A count is hidden while a day has unsaved changes, rather than having the frontend repeat the calculation and risk disagreeing with what members can actually book. The count describes an ordinary day, so a day when the clocks change can have fewer slots.

**Saving replaces the whole week.** The API takes the full week and swaps it in one transaction, so an invalid row changes nothing. A day left out is a day off.

### Daylight saving

Each working day starts and ends at its wall-clock times, so a 09:00 start stays at 09:00 for the professional and its UTC time moves when the clocks change. Slots are then stepped through that day in real time, 60 minutes apart, which means they can't overlap, however far the clocks move. On the changeover days themselves:

- **Clocks go forward:** no slot starts in the missing hour. A session running across it can still appear on the calendar, but `Appointment` refuses it, as described under "A booked time must be valid for both people". Working hours that start in the missing hour begin once it's over, so 02:30 becomes 03:30. An end time in the missing hour means the moment the clocks jumped, so a session can't run past the time the professional meant to finish.
- **Clocks go back:** slots touching the repeated hour aren't offered, because stored local time couldn't tell the two apart, so the day can have fewer slots.
- **Slots later that day:** in a timezone whose clocks move by 30 minutes, like Lord Howe Island, slots after the change can land on different wall-clock minutes for that one day.

## Calendar and appointments

**Preventing double-booking.** A PostgreSQL exclusion constraint on `appointments` rejects overlapping booked rows for the same professional. A check in Rails followed by an insert can't do this, because two requests can both pass the check before either one inserts. The database settles the race: the first commit wins, and the other request gets a clear 409 message. All of a professional's appointments are stored in that professional's timezone, so comparing their local times is correct. Specs race real threads against the real database. They also found that overlapping inserts can deadlock on the constraint check. Postgres aborts one, which never allows a double-booking. That member is told the time can't be booked right now, rather than getting a server error. It isn't retried, which keeps booking simple, so they may need to try again themselves.

**A member may book overlapping sessions.** Only a professional is limited to one appointment at a time. A member can book sessions with different professionals at the same time, which keeps booking simple and avoids a lock on the member's row.

**The server decides what a slot is.** An appointment request carries the professional, then the date, start time and end time on the professional's clock, exactly as the calendar gave them. The member comes from the login, the timezone comes from the professional, and all three values must match a slot generated right now, so a client can't change a session's length. The trade-off is that a clock time only means something together with a timezone: if a professional's timezone could change between the calendar loading and the booking, the same values could match a different real moment. The app has no way to change a timezone today, but adding one would mean checking for this. That rules out past times, made-up times and anything beyond the 4-week window. A session's stored `ends_at` means existing sessions keep their length if the session length ever changes.

**Appointments store local time plus one timezone.** `appointment_date`, `start_time` and `end_time` are the date and times on the professional's clock, and `timezone` is their IANA name at booking. An appointment then stays at the same local time if a government changes its timezone rules, and it reads naturally for the professional. The costs are that real moments must be calculated when comparing or sending times, and that local time can't identify one of the two repeated times when the clocks go back. So slots that start in, end in or cross the repeated hour aren't offered that day. Every stored appointment then reads back as exactly one moment. A session can't cross midnight, because working hours can't, so one date is enough. The app's `Time.zone` must stay UTC, because Rails would otherwise shift `start_time` and `end_time` when saving them.

**A booked time must be valid for both people.** Before an appointment is created, `Appointment` checks its date, clock times and timezone. The stored times must exist on the professional's clock. Then, in the professional's timezone and the member's, each end must mean exactly one moment and the clocks must not change during the session. So when 02:00-03:00 doesn't exist, 01:30-03:20 is refused even though it lasts a real 50 minutes. The rule doesn't care why a clock moved, so it covers daylight saving and a country changing its timezone, as long as the server's timezone data knows about the change. The calendar stays simple and can still show such a time, so a member can pick one and then be asked to choose another. The check only runs when an appointment is created, so a timezone rule changing afterwards can't stop it being cancelled, but it also means nothing flags an existing appointment that such a change makes invalid.

**The calendar is prepared on the server.** The API sends each day and time already converted to the member's timezone and grouped under the member's own date, so a slot can appear on a different date for the member than for the professional. This also means the frontend can't accidentally use the browser's timezone, which can differ from the one chosen at sign-up, for example when someone is travelling. Each slot also carries the time on the professional's clock, which the confirmation screen shows, so the two can be compared before booking. The professional's timezone was already visible to members in the list of professionals, so this exposes nothing new.

**Only free slots are exposed.** The calendar response has no appointment or member data, so a member can't see who else has booked.

**My sessions comes from one endpoint for both roles.** `GET /api/v1/appointments` returns the logged-in person's own sessions, so no id in the request can reach someone else's. `SessionList` formats each date and time on that person's clock, and orders by the real moment, so sessions with professionals in different timezones still sort correctly. A member gets upcoming and past sessions, including cancelled ones, marked as such, so they can see what happened to a booking. A professional gets only upcoming booked sessions, which is the schedule they work to, with each member's name but not their email. A session moves to past when it ends, not when it starts. Past sessions aren't paginated, which is fine at this scale but would need a limit for long histories.

**Cancelling and rescheduling share one rule.** `AppointmentPolicy` decides whether a session can change, and why not: a member up to 24 real hours before the start, a professional until it ends, and nobody once it's cancelled or over. The 24 hours are measured between real moments, so a clock change in between doesn't shorten or lengthen the notice. The cancel and reschedule endpoints and My sessions all ask it, so the buttons a person sees and what the server accepts can't disagree, and the frontend has no time logic. Within 24 hours the member sees the reason instead of the buttons. Only members reschedule, because the brief only gives professionals cancel.

**Rescheduling moves the same appointment.** It updates the date and times of the existing row, which stays `booked` and keeps its id, so it can be rescheduled as often as the member likes and they can never end up with no session or two. It locks the row, checks the rule, and only accepts a real slot, found the same way as for booking (`SlotGenerator#find`). The exclusion constraint and the "valid for both people" check apply to the new time, because that check runs whenever an appointment's time changes. If anything fails, the update rolls back and the session keeps its old time. Updating the row frees the old time in the same step, so a member can move to a time that overlaps their current one. Two reschedules of the same session at once take turns on the lock, and the last one wins. A spec races real threads to show this. The trade-off is that the old time isn't recorded anywhere, so there's no history of moves. Someone else's session returns 404, the same as one that doesn't exist.

**Slots booked before working hours change stay booked.** Changing hours doesn't cancel anything. Any generated slot overlapping an existing appointment is left out, even if the two no longer line up.

**Reminders are rows, each with its own scheduled job.** Booking creates one `reminders` row per lead time for the member and the professional (24 hours and 1 hour before), in the same transaction as the appointment, and leaves out any whose time has already passed. Each row gets a `DeliverReminderJob` queued with `wait_until` its time, and stores that job's id. Rescheduling and cancelling replace the undelivered rows in the same transaction as the change, discard their queued jobs, and queue new ones for the new time (none for a cancellation). A cancelled session gets none. Delivered reminders are never touched, because they are already someone's notifications. Each row stores `minutes_before` rather than a fixed kind, and the lead times are one list in `Reminder::LEAD_TIMES`, so they can change without a migration. The database only checks that the number is positive, and the message describes any value ("in 24 hours", "in 30 minutes").

**The jobs follow the transaction, and the appointment's lock decides.** The queue is a separate database, so a job can't be part of the appointment's transaction. Each reminder row is created with its job id already chosen, and its job is queued under that id once the transaction commits. Old jobs are discarded after commit too, so a booking or change that rolls back leaves the queue as it was. By then the change is saved, so if the queue fails, the error is reported and the user still gets a success, rather than a 500 for a booking that went through (and a retry that finds their own slot taken). A job that was already running can't be discarded, and Solid Queue runs a job at least once, not exactly once. So the job only passes a reminder id, and delivery takes the appointment's row lock, the same one rescheduling and cancelling take, before it reads the reminder. A change in progress therefore finishes first, and delivery finds its replaced reminder gone; a stale job or a second run likewise does nothing. A spec races a delivery against a change on real threads. Solid Queue keeps scheduled jobs in Postgres, so a job due while the server was down runs when it comes back. Such a late reminder is dropped if its session has started or a later reminder to the same person is already due, and one more than a few minutes late says how long is really left ("starts in 21 hours") rather than its lead time. Development uses Solid Queue as production does, with its own `thoughfull_development_queue` database, and runs it inside Puma, so `bin/rails server` delivers reminders without a second process. Reminders arrive on time rather than on a polling interval. The trade-off is that if the queue fails, or the server stops between the commit and queueing, those reminders are never sent, because nothing sweeps for missed ones (a periodic job that queues any due pending reminder would close that gap).

**A delivered reminder is the notification.** There is no separate notifications table: delivering a reminder writes its message, on the recipient's own clock and naming the other person, and the notification list is that person's delivered reminders, newest first, with a `read_at`. The navbar shows the unread count, refreshed every minute by the frontend, and the list has "Mark all as read". That sends the newest `delivered_at` the person was shown, and only reminders delivered up to then are marked, so one that arrives while the page is open stays unread. The list returns the latest 50.
